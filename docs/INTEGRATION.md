# План подключения фронтенда к API

**Цель:** каждый экран, подключённый к настоящему API, работает с первого раза — без неожиданных полей, статусов и ошибок.

**Как этого добиться:**
1. Одна форма данных на всех — сгенерированная из кода API. Рукописных типов провода нет.
2. Все расхождения между готовыми экранами и контрактом закрываются **до** кода (раздел 3).
3. Каждый экран подключается одним PR веба, и в этом же PR удаляется его заглушка.
4. Каждое подключение проверяется по одному и тому же списку (раздел 8).

Документ дополняет `docs/PLAN.md` (что и зачем) и `docs/contracts/` (формы данных). Если они расходятся, прав `docs/contracts/`, а этот файл исправляется в том же PR.

## 1. Решения от 22.09

| Вопрос | Решение |
|---|---|
| Где демо на питче | **Оба окружения.** Сервер с HTTPS — для ссылки жюри. Ноутбук с Docker Compose — запасной путь на сцене, работает без сети (раздел 9) |
| Запасной режим фронтенда | **Нет.** После подключения заглушки экранов удаляются. Запасной путь — `DEMO_MODE` + `GATEWAY_MODE=replay` в самом API. Стенд платформы inVision остаётся на MSW: это имитация чужой системы, а не наш API |
| Данные на вебе | **TanStack Query** поверх сгенерированного клиента `openapi-fetch` |
| Сюрпризный вопрос | **Видео + голос**, новый слайс S (раздел 10) |

## 2. Как веб ходит в API

```
Браузер ──/api/v1/*──▶ Next.js (BFF, сервер веба) ──X-API-Key──▶ api:3001 ──X-Internal-Token──▶ ml:8000
```

- **Браузер никогда не видит ключ.** Все запросы идут на свой же адрес `/api/v1/*`. Route handler `apps/web/app/api/v1/[...path]/route.ts` добавляет `X-API-Key` и пересылает запрос на `API_INTERNAL_URL`. CORS не нужен.
- **Какой ключ — решает роль из cookie `invision-demo-role`.** Сейчас роль лежит в `localStorage`, и сервер её не видит, поэтому она переезжает в cookie (шаг W0.2). Ключи лежат в переменных окружения сервера веба, никогда не `NEXT_PUBLIC_*`:

| Роль в демо | Переменная | Роль в API |
|---|---|---|
| Кандидат | `WEB_API_KEY_PLATFORM` | `platform` |
| Интервьюер | `WEB_API_KEY_INTERVIEWER` | `interviewer` |
| Комиссия | `WEB_API_KEY_COMMISSION` | `commission` |
| Админ | `WEB_API_KEY_ADMIN` | `admin` |

- **Прокси пересылает всё как есть:** метод, тело (включая `multipart` для аудио и видео — потоком, без буферизации), заголовки `Idempotency-Key` и `Content-Type`, статус и тело ответа. Он ничего не переписывает и не кэширует. `GET /api/health` веба — своя живость; `GET /api/v1/health` — живость API через прокси.
- **На сервере наружу открыт только веб.** Caddy отдаёт `https://<домен>/` → `web:3000`, а `api` и `ml` доступны только внутри сети Docker. Когда inVision понадобится прямой доступ к `/v1`, это отдельное решение с отдельным маршрутом.

### Правила TanStack Query

| Правило | Значение |
|---|---|
| Где подключён | `QueryClientProvider` в `app/(product)/layout.tsx`. Стенд его не использует |
| Ключи запросов | `['candidates']`, `['candidate', id, 'progress']`, `['brief', candidateId]`, `['simulation', id]`, `['assessment', id]`, `['feedback', id]`, `['interview', id]`, `['draft', interviewId]`, `['surprise', id]`, `['admin', 'overview']`, `['admin', 'audit']`, `['scenarios']` |
| `staleTime` | 5 с. Для `['scenarios']` — `Infinity` |
| Повторы `GET` | ≤ 2 при сетевой ошибке и `5xx`, пауза 500 мс → 1500 мс. **Никогда при `4xx`** |
| Повторы изменений | Автоматически — нет. Кнопка «Повторить» отправляет **тот же** `Idempotency-Key`, поэтому повтор не создаёт дубль |
| Опрос | Только пока статус промежуточный: `transcriptStatus: "transcribing"` — каждые 2 с; прогресс кандидата на главных — каждые 5 с; журнал админа — каждые 5 с. Останавливается на финальном статусе |
| После изменения | Инвалидируются ровно зависимые ключи — таблица в разделе 4 |

### `Idempotency-Key`

Ключ — `crypto.randomUUID()`. Он создаётся **один раз на действие пользователя** (нажатие «Сохранить», отправка реплики), хранится в состоянии мутации до успеха и переиспользуется при повторе. Новое действие — новый ключ.

## 4. Слой данных во фронте

Новые файлы веба (всё в `apps/web`, владелец — Мейірбек):

| Файл | Что делает |
|---|---|
| `app/api/v1/[...path]/route.ts` | BFF-прокси (раздел 2) |
| `lib/api/serverKeys.ts` | `server-only`: роль → ключ из окружения. Неизвестная роль — `interviewer` |
| `lib/api/client.ts` | `createClient<paths>({ baseUrl: '/api/v1' })` из `@invision/api-client` |
| `lib/api/errors.ts` | Код ошибки → текст на EN/RU; неизвестный код → общий текст с `traceId` |
| `lib/api/queries/<resource>.ts` | Хуки TanStack Query: один файл на ресурс |
| `lib/api/mappers/<resource>.ts` | Ответ API → форма экрана. Компоненты экранов не меняются |
| `lib/api/mappers/*.test.ts` | **Золотые тесты:** каждый пример из `docs/contracts/examples/` через маппер даёт ровно те данные, которые экран показывает сейчас |

**Какие ключи сбрасывает каждое действие:**

| Действие | Сбрасывает |
|---|---|
| Отправка реплики | `['simulation', id]` |
| Завершение симуляции | `['simulation', id]`, `['candidate', id, 'progress']`, `['candidates']` |
| Загрузка записи интервью | `['interview', id]`; дальше опрос до `ready` |
| Сохранение баллов | `['interview', id]`, `['draft', id]`, `['candidate', id, 'progress']` |
| Запрос черновика | `['draft', id]` |
| Сброс демо | всё (`queryClient.clear()`) |

**Что удаляется и когда.** Заглушка экрана удаляется в том же PR, где подключается его хук. Файлы, которые больше ничего не используют, удаляются вместе с последним экраном, который их использовал.

| Заглушка | Удаляется в шаге |
|---|---|
| `lib/simulation/previewDriver.ts`, `previewScenario.ts` | W2 |
| `lib/report/preview.ts` | W3 |
| `lib/brief/preview.ts` | W4 |
| `lib/interview/preview.ts`, `previewServer.ts`, `store.ts` | W5 |
| `lib/demo/world.ts` и `lib/demo/candidates.ts` | W6 — последним: их заменяют `progress` и `candidates` |

## 6. Как не конфликтовать

| Файл | Владелец | Правило |
|---|---|---|
| `pnpm-lock.yaml` | кто добавил зависимость | **Никогда не мержить руками.** При конфликте взять версию `main`, выполнить `pnpm install` и закоммитить. Зависимости добавлять отдельным маленьким PR и мержить в тот же день |
| `apps/api/openapi.json` | Айбек | Только генерация. При конфликте — перегенерировать |
| `packages/api-client/src/generated/*` | генератор | Только `pnpm api:generate`. Кто меняет API, перегенерирует в том же PR |
| `services/ml/openapi.json`, `apps/api/src/ai-client/*` | Наурызбек и Айбек | То же правило |
| `docs/contracts/*`, `docs/SPEC.md` | все трое | Меняются **только** контракт-PR с ревью обоих затронутых. Во время реализации слайса контракт заморожен |
| `.env.example` | Мейірбек | Секции `# Web`, `# API`, `# ML` — каждый добавляет строки только в свою секцию |
| `docker-compose.yml` | Айбек | Блок `web` пишет Мейірбек через PR в ветку Айбека, а не отдельным PR |
| `Caddyfile`, `docs/DEPLOY.md` | Мейірбек | — |
| `apps/api/prisma/*` | Айбек | Миграции только последовательно, одна ветка за раз |
| `seed/**`, `config/**`, `fixtures/**` | Наурызбек | Веб читает примеры из `docs/contracts/examples/`, а не из `seed/` |
| корневой `package.json` | Мейірбек | Скрипты других частей добавляются через PR с ревью Мейірбека |

**Главные правила:**
- Одна ветка — один человек.
- Перед ревью: `git fetch && git rebase origin/main`.
- Контракт-PR мержится первым, в тот же день.

## 7. Состояния каждого экрана

| Экран | Загрузка | Пусто или ещё нет | Ошибки |
|---|---|---|---|
| Главные | Скелет таблицы | «B и C появятся с seed»; при `pending` — «готовится» | Сеть или `5xx`: баннер «Не удалось обновить» и последние данные |
| Симуляция | Скелет переписки | Нет симуляции → создаётся | `409 TURN_IN_FLIGHT`: «Подождите ответа»; `409 SIMULATION_FINISHED`: экран конца; `400`: текст под полем; `503 AI_*`: «Персонаж не отвечает — повторить», реплика не теряется |
| Отчёт | Скелет карточек | `progress.assessment: pending` → «Отчёт готовится», опрос | `403`: «Эта роль не видит отчёт»; `404`: «Отчёт не найден» |
| Отзыв | Скелет | «Будет готов после проверки» | `404` |
| Бриф | Скелет | `pending` → «Бриф готовится», опрос | `503 AI_*`: «Не удалось подготовить — повторить» |
| Интервью | Скелет | Запись не загружена → рекордер | `400 CONSENT_REQUIRED` (не должно случиться: кнопка выключена); `409 TRANSCRIPT_MISSING` → ждём и опрашиваем; `409 DRAFT_LOCKED` → замок; `409 SCORES_ALREADY_SAVED` → перечитать; `failed` → «Расшифровка не удалась — загрузить снова» |
| Админ | Скелет | Журнал пуст → текст | `DEMO_MODE=false` → кнопки демо скрыты |

**Тексты ошибок** живут в `lib/api/errors.ts`: EN и RU, для кандидата только EN. Экран никогда не показывает `message` сервера как есть, только текст по `code`; `traceId` выводится мелко — его можно продиктовать.

## 8. Проверка подключения

Экран считается подключённым, когда:
1. его заглушка удалена, и `git grep` по её имени пуст;
2. золотой тест маппера зелёный на сгенерированных типах;
3. на ноутбуке `docker compose up` с `DEMO_MODE=true GATEWAY_MODE=replay` и **выключенным Wi-Fi** экран проходит свой сценарий;
4. состояния из раздела 7 проверены: выключить `ml` → ошибка ИИ показана, данные не потеряны;
5. в консоли браузера нет ошибок, кроме ожидаемого `401` стенда.

**Сквозной сценарий** — повторяет то, что уже проходит на превью (скрипт Playwright переносится в `apps/web/e2e/demo.spec.ts`):
1. Кандидат играет симуляцию.
2. Комиссия видит отчёт и открывает цитату.
3. Интервьюер открывает бриф, загружает запись, ставит баллы и видит черновик.
4. Админ видит в журнале все шаги.
5. Сброс демо возвращает всё к началу.

## 9. Два окружения демо

| | Ноутбук (запасной путь на сцене) | Сервер (ссылка для жюри) |
|---|---|---|
| Запуск | `docker compose up` | `docker compose -f docker-compose.yml -f docker-compose.server.yml up -d` + Caddy |
| Сеть | Не нужна | Нужна |
| ИИ | `GATEWAY_MODE=replay`, `DEMO_MODE=true` | `replay` на питче; `live` — только с `BUDGET_USD_CAP` и ключом с лимитом |
| Микрофон и камера | Работают: `localhost` считается безопасным | Работают только по HTTPS — его даёт Caddy |
| Адрес | `http://localhost:3000` | `https://<домен>` |
| Сброс перед показом | Админ → «Сбросить демо» | То же |

**Репетиция за день до питча:** оба окружения, сквозной сценарий трижды подряд без ошибок, затем с выключенной сетью на ноутбуке.

## 10. Сюрпризный вопрос — видео + голос (слайс S)

**Зачем.** Видео-ответы на опубликованные вопросы кандидат может отрепетировать. Один неожиданный вопрос по его же анкете показывает, как он думает без подготовки.

**Поток кандидата** (английский):
1. На главной появляется шаг 3 «Короткий вопрос».
2. Экран-инструктаж: одна попытка, 90 секунд на ответ, камера и микрофон. Проверка устройств — с превью камеры и уровнем звука, ничего не записывается. **Две отдельные галочки согласия:** на видео и на обработку ответа.
3. «Показать вопрос» — вопрос появляется, запись стартует через 10 секунд.
4. Запись останавливается сама на 90-й секунде или кнопкой «Готово».
5. Загрузка. Вторая попытка невозможна — это правило сервера.

**Правила сервера** (`docs/contracts/api.md`, раздел «Surprise question»):
- `POST …/start` выдаёт вопрос и **серверный** дедлайн; повторный старт → `409 ALREADY_STARTED`;
- загрузка после дедлайна + 15 с → `409 DEADLINE_PASSED`;
- без двух согласий → `400 CONSENT_REQUIRED`;
- **видео не уходит ни в одну модель:** API вынимает звук (`ffmpeg`), ML его расшифровывает, в модель попадает только текст;
- видео смотрят только `interviewer`, `commission` и `admin`, каждый просмотр пишется в аудит;
- видео удаляется при сбросе демо и через 30 дней после решения;
- в репозиторий записи не попадают никогда. Для демо команда записывает синтетические ответы с собственного согласия.

**Кто что видит:**

| Роль | Что видит |
|---|---|
| Кандидат | Вопрос и свою запись до отправки. Никакой оценки |
| Интервьюер | В брифе блок «Сюрпризный ответ»: вопрос, расшифровка, плеер; цитаты с источником `surprise_answer` |
| Комиссия | То же в отчёте |
| Админ | Статус в модулях и журнале |

**Готово, когда:** вопрос сгенерирован по анкете A; одна попытка держится сервером; расшифровка и цитаты появляются в брифе; видео проигрывается только ролям сотрудников; `platform` получает `403` на видео.
